## 1. 环境搭建与 OLED 屏幕驱动

**完成时间：2026-10-06**

### 1.1 功能描述
本板块对应机器人的**“状态可视化”功能**：在电控开发的初期，需要建立一个稳定可靠的 STM32 开发环境，并驱动 OLED 屏幕，用于在脱离串口打印的情况下，实时显示底盘调试参数。

### 1.2 开发历程
**起点：编译器版本冲突与核心报错**
基于 STM32F103C8T6 核心板建立基础工程。为了快速驱动屏幕，我们导入了商家基于标准库的旧版工程，结果遭遇了第一波“暴击”：
*   **ARM 编译器报错**：工程默认使用 ARM Compiler 5，而新版 Keil 默认安装的是 V6，导致 `core_cm3.c` 中的底层汇编报错。
*   **解决路径**：未选择降级编译器，而是在魔术棒（Options for Target）中将编译器切换为 `V6`。随后，针对 `core_cm3.c` 的内联汇编不兼容问题，采取了“配置宏屏蔽法”以及修改底层裸函数语法，最终实现零报错编译。

**I2C 通信建立与画面方向校准**
OLED（1.3寸，SH1106 驱动）采用 I2C 协议。在实际接线中，明确了 SCL 对应 PB6，SDA 对应 PB7。烧录后屏幕亮起，但出现**画面完全上下颠倒**的现象。查阅底层驱动代码发现，初始化指令中关于扫描方向的配置冲突：将原代码的 `0xC8`（上下翻转）修改为 `0xC0`（正常方向），验证了硬件物理寻址与软件逻辑寻址需要完全匹配。

> **反思**：这一阶段最大的收获是“**不要用新工具去强行兼容旧代码**”。新版的 ARM Compiler V6 对语法更严格，商家的旧标准库存在历史遗留问题。遇到编译报错，先看底层依赖，再决定是降版本还是重写语法。

## 2. DRV8833 驱动与单电机控制

**完成时间：2026-10-08**

### 2.1 功能描述
本板块对应机器人的**“基础运动执行”功能**：通过 STM32 控制驱动芯片，让 TT 马达按照预期的方向旋转，验证供电、驱动芯片与执行机构的控制链路。

### 2.2 开发历程
**核心难点：DRV8833 的使能逻辑**
初次接线测试时，代码已正确将对应引脚置高/置低，但电机纹丝不动。排查了代码、杜邦线、电源，最后定位到 DRV8833 芯片的 **`STBY`（待机/使能）引脚**。查阅数据手册发现，该芯片内部有一个休眠逻辑，若 `STBY` 引脚处于悬空（低电平），芯片内部的 H 桥全部截止。将 `STBY` 引脚强制接高电平（STM32 的 3.3V）后，电机立刻恢复响应。

**“生死线”：共地（GND）问题的深度剖析**
在测试双电源（电脑 USB 供单片机 + 充电宝供驱动板）时，系统出现严重乱码，电机甚至自激抖动。原理在于：STM32 的 GPIO 输出高电平是相对于其自身的 GND 而言的。如果驱动板的 GND 与 STM32 的 GND 没有连接，驱动板接收到的信号就像是“没有参考的海市蜃楼”，逻辑乱飞。将所有模块的 GND 用一条总线全部串联后，系统恢复稳定。

> **反思**：在混合控制中，“地”是一切信号的基石。之前一直以为只要代码对、电压对就行，实际上共地才是通信的第一步。另外，牢记 `STBY` 这个隐藏开关，是新手最常踩的坑。

## 3. PS2 无线手柄通信解析

**完成时间：2026-10-10**

### 3.1 功能描述
本板块对应机器人的**“指令输入”功能**：解析 PS2 无线手柄与接收器之间的通信协议，获取摇杆的 0~255 模拟量，为底盘的精确控制提供输入源。

### 3.2 开发历程
**锁定款手柄的特殊配对机制**
本次使用的是商家提供的“锁定款”PS2 手柄。首次上电时，接收器指示灯常亮，但无法获取数据。根据指导手册，锁定款必须手动匹配：用顶针戳接收器外壳的隐藏小孔，使灯从“闪烁”转为“常亮”。且配对成功后，需确保手柄处于“模拟红灯模式”，而非“数字模式”，数字模式不能按连续模拟摇杆数据直接用于本版控制。

**SPI 模拟通信与安全锁保护**
PS2 手柄使用自定义的类 SPI 协议，依赖正确的时钟与数据采样时序。我们在底层驱动中遇到了一个致命问题：未连接手柄时，底层读取到的摇杆数据全为 0，导致混控算法输出“全速前进”指令，一开机四个轮子就狂转。
*   **迭代与改进**：在解析手柄模式时加入了“数据校验安全锁”。只有识别到合法模式，才允许将数据送入电机混控，否则撤掉电机驱动输出。并且将手柄的“死区”扩大到 50，历史记录认为改善了“摇杆回中不彻底导致电机停不下来”的现象；未附静止漂移数据，后续仍需实测，且死区不能消除机械传动间隙。

> **反思**：处理传感器数据时，永远不要相信“绝对理想状态”。必须加入超时判断、异常值过滤和死区处理。这是系统健壮性设计的入门。

## 4. 4WD 麦轮底盘运动学混控

**完成时间：2026-10-12**

### 4.1 功能描述
本板块对应机器人的**“底盘全向移动”功能**：利用麦克纳姆轮的特性，通过混控算法将摇杆的前后、左右、旋转指令，解算并分配给四个电机。

### 4.2 开发历程
**硬件引脚的“绝地求生”**
在分配引脚时发现，STM32F103C8T6 核心板在当时接线条件下**没有可用的 PB2 引出点**。为了凑齐四个电机所需的 8 个 GPIO，我们被迫进行引脚重映射，将左后轮的信号线改为了 PA3 和 PB3。

**致命的 JTAG 引脚复用冲突**
接线完成后，出现了极其诡异的现象：左前、左后、右前都能正常控制，唯独右后轮“格格不入”。查阅数据手册发现，PB3、PB4 默认被分配给了 JTAG 调试接口，如果不解除复用，根本无法作为普通 GPIO 使用。在 main 函数开头加入 AFIO 时钟开启与 JTAG 释放代码后，右后轮终于被收复。

**麦轮混控算法**
基于经典的四轮 X 型布局编写混控公式（fl=ly+lx+rx; fr=ly-lx-rx 等）。若出现某轮反转，无需改代码，直接对调该轮马达连接 AO1/AO2 的物理线序，完成了控制逻辑与物理执行的对齐。

> **反思**：这一板块是对“硬件与软件耦合”体会最深的一次。硬件上缺少引脚、默认功能被复用，都必须在软件初始化阶段通过底层寄存器去解锁。

## 5. 供电系统架构与防打架设计

**完成时间：2026-10-14**

### 5.1 功能描述
本板块对应机器人的**“动力与电源管理”功能**：从初期使用充电宝+面包板测试，迭代到符合比赛规范的 18650 锂电池（7.4V）+ DC-DC（5V）动力系统。

### 5.2 开发历程
**早期草稿方案的证伪**
初期采用了“充电宝接降压模块供 5V” + “电脑 USB 插 STM32” 的双电源方案。上电后 STM32 主芯片与外部晶振出现严重发热。历史记录将原因初步归为“电源倒灌”。本次未附原始电路及电流测量，不能仅凭发热确认唯一原因；需要结合供电路径、短路和受损器件复核。由此确立了避免未经隔离的不同电源直接并联的原则。

**正式方案：18650 + 降压模块的过流保护**
改用两节 18650 串联后，在接入前轮 DRV8833 的瞬间，供电模块直接断电。经排查，是驱动模块引脚发生物理短路，触发了电源模块的过流保护。重新整理绝缘走线后恢复。最终确定供电拓扑：一路 7.4V 直供 DRV8833，另一路降压 5V 供主控，所有地线汇聚共地。

> **反思**：电源问题是所有电控灾难的源头。强电与弱电必须分离，接口必须做绝缘处理。

## 6. 开源项目与第三方资源说明

### 6.1 基础驱动库来源
*   **项目名**：XTARK OpenCTR / PS2 无线手柄例程
*   **作者**：塔克创新（XTARK）
*   **使用内容**：ax_ps2.c、ax_delay.c 等标准库底层文件。
*   **使用方式**：用于直接解析 PS2 手柄的软件 SPI 时序。未修改底层通信时序，仅在其基础上重写了 main.c 中的麦轮混控与安全锁逻辑。
*   **修改说明**：将缺失的 PB2 引脚替换为 PA3；加入了 JTAG 释放代码，并完善了手柄死区与安全保护逻辑。

### 6.2 工具链与软件
*   **Keil MDK-ARM V5**：代码编写与编译。
*   **ARM Compiler V6**：解决旧版库兼容性问题。
*   **STM32CubeProgrammer**：用于全片擦除，解除芯片锁死。
*   **CH340 + 串口助手**：用于调试手柄数据输出。

### 6.3 历史日志记录的逻辑名称（非本次已上传源码）
*   `PS2_Safety_Lock`：检测手柄未配对或切数字模式时撤掉驱动输出（原程序为滑行状态）。
*   `Deadzone_Filter`：扩大死区，屏蔽部分中位输入偏差（不能消除机械传动间隙）。
*   `JTAG_Release`：释放 PB3/PB4 复用功能。
